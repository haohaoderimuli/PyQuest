# 联合冲刺 · 订单收入口径调整

这是 TestLab / Data Quest / PyQuest **三个平台共用的一份需求**。三个人拿同一份需求、同一份数据各做各的活，最后把三份产物放在一起验，看能不能上线。

不是三道独立的题。口径一改，另外两边的产物必须跟着改 —— 这就是真实项目里「影响到下游」的意思。

## 背景

上个月的财报多算了退款单。财务要求改口径，产品把工单转给三组人：

- **开发（PyQuest）**：写处理脚本，按新口径出 `metrics.json`
- **测试（TestLab）**：按 AC 写用例、提缺陷、给准出结论
- **分析（Data Quest）**：算指标、和财务侧对账、给上线建议

## 需求原文（工单里只有这一段）

> 订单收入口径调整：退款不算收入，跨月订单按支付时间归月，按渠道拆。数据给我，财务侧期望也给你，自己对。

## 验收标准 AC（三方共用，不许各写各的）

| AC | 内容 | 判据 |
| --- | --- | --- |
| AC1 | 只统计 `status == "paid"` | `refunded` / `pending` 不计入 |
| AC2 | 按 `paid_at` 归月 | `order_date` 在 5 月但 `paid_at` 在 6 月的订单算 6 月 |
| AC3 | 按 `channel` 拆金额 | App / Web 两个渠道分别汇总 |
| AC4 | 与财务侧对账差额为 0 | 容差 0.005 元 |

## 数据

`data/orders.csv` 与 `data/finance_expected.csv` 在三个平台里各有一份**内容完全相同**的副本。
中心目录 `joint-sprint/` 是源，`sync.py` 负责同步；`check.py` 会比对三份副本的 SHA-256，改数据不认。

字段：`order_no, channel, amount, status, order_date, paid_at`。
注意 O001 下单在 5/31、支付在 6/1；O003 / O007 是退款单且金额不小 —— 这两处是坑。

## 三份产物

在各自平台做完之后，把产物复制到 `deliverables/`：

| 文件 | 谁出 | 内容 |
| --- | --- | --- |
| `dev.json` | PyQuest | 口径选择、summary、月度渠道金额 |
| `qa.json` | TestLab | AC 执行结果、关联到 AC 的缺陷、准出结论 |
| `analyst.json` | Data Quest | 指标、对账差额、上线建议 |

字段模板在 `deliverables/`，参考解在 `solution/`。**别看参考解再写**，先做，卡住再对。

## 联合验收

```
cd joint-sprint
python check.py
```

它真读三份产物，检查：

1. 三份文件都是合法 JSON，`brief_id` 都是 `rev-rule-v2`
2. 开发与分析的口径字段一致（`paid_only` / `paid_at`）
3. 开发与分析的指标**逐个数相同**（不是各算各的）
4. 月度渠道金额与财务侧期望逐格比对，容差 0.005
5. 测试至少提一条缺陷，且每条都挂到具体 AC 上
6. 测试的准出结论与分析的上线建议一致
7. 三份数据副本的 SHA-256 与中心目录一致

退出码 0 全绿，1 有 FAIL。任何一边改了口径而对账没跟着改，都过不了。

## 边界

这是一个人写三份产物，模拟的是三个角色的**交付物对齐**，不是真人协作。真实项目里还要开会、争论、走审批，网页里造不出来。这里练的是最硬的那一点：**同一份需求下来了，三个人的产出必须对得上**。
